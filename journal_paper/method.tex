\section{Method}\label{method}

This study proposes a reusable local benchmarking pipeline for selecting embedding models under corpus-specific Retrieval-Augmented Generation (RAG) requirements. The method is organized as a staged workflow that transforms local document collections into benchmark-ready corpora, synthetic queries, relevance judgments, per-model vector indexes, and structured reports. The ordering of these stages is deliberate: each intermediate artifact becomes a controlled input to the next stage, which allows all candidate embedding models to be evaluated under the same benchmark evidence rather than under model-specific or manually curated test sets.

\subsection{Pipeline Overview}\label{pipeline-overview}

The pipeline operates at the dataset level and begins with explicit dataset routing, as illustrated in Figure~\ref{fig:method_pipeline_workflow}. Each corpus is processed in isolation so that document inputs, chunked corpora, synthetic queries, qrels, vector collections, and reports remain separated across datasets. This design reduces cross-dataset contamination and allows the same methodological template to be applied repeatedly to document collections that differ in language, domain, and scale. After routing, the workflow advances through document ingestion, chunking, query generation, and relevance construction, thereby producing the benchmark artifacts required for comparative retrieval.

Once these shared artifacts have been created, the pipeline branches into model-specific indexing and evaluation. Separate vector collections are built for each candidate embedding model, and each model is evaluated against the same query and qrels resources rather than against model-specific or manually curated evidence. The final stage consolidates the resulting outputs into dataset-level reports and, when multiple corpora are available, into an aggregate comparison report. The sequence of stages and their intermediate products are summarized in Table~\ref{tbl:method_pipeline_stages} and illustrated conceptually in Figure~\ref{fig:method_pipeline_workflow}.

\subsection{Corpus Preparation}\label{corpus-preparation}

The first stage converts each local document collection into a benchmarkable text corpus. Source documents are ingested from the local corpus and parsed into textual segments; in the present manuscript snapshot, these source documents are provided as PDF files. To preserve local context while keeping units manageable for downstream embedding models, the extracted text is segmented by recursive character-based chunking with controlled overlap between adjacent segments. This strategy reduces the probability that semantically dependent passages are split into entirely disconnected units, while still producing retrieval items that can be embedded and indexed efficiently. The chunking settings used in this stage, together with the shared workflow parameters that govern later stages, are listed in Table~\ref{tbl:method_workflow_parameters}.

Dataset-level isolation is maintained during corpus preparation. Each dataset yields its own chunked corpus and retains its own storage path for downstream artifacts. As a result, the same pipeline can be reused across multiple corpora without mixing documents, collections, or reports between experiments.

\subsection{Synthetic Query and Relevance Construction}\label{synthetic-query-and-relevance-construction}

After corpus construction, the pipeline constructs benchmark queries and relevance judgments through the sequence shown in Figure~\ref{fig:method_qrels_workflow}. Each instance begins with a seed chunk sampled from the corpus. Rather than relying on externally authored questions, the method prompts a large language model to generate a concise natural-language query in the same language as that sampled chunk. This design keeps query formulation anchored to the linguistic and topical properties of the target corpus while avoiding the cost of manually preparing a query set for each new dataset.

Relevance construction then proceeds from the generated query. The system retrieves a bounded candidate pool of corpus chunks, with the candidate set size fixed by the shared workflow parameters in Table~\ref{tbl:method_workflow_parameters}, and presents these query--chunk pairs for binary relevance labeling. The output of this stage is therefore not a free-form annotation record, but a qrels resource in which each candidate is marked as relevant or non-relevant for later retrieval evaluation. Because the query set and qrels are created before comparative model assessment begins, all embedding models are evaluated against the same benchmark artifacts under a controlled protocol.

\subsection{Embedding Index Construction}\label{embedding-index-construction}

The comparative evaluation stage uses a fixed set of sentence-transformer models spanning lightweight, higher-capacity, and multilingual alternatives within a single benchmarking design. Each model is assigned its own vector collection so that embedding generation, storage, and retrieval remain isolated across models. This separation is methodologically important because it ensures that observed differences arise from the embedding models themselves rather than from shared or overwritten index state. The exact benchmarked model roster is specified in the experimental setup. \citep{SentenceTransformers_Pretrained}

Model-specific collections are built from the same chunked corpus. This means that corpus content, query set, and relevance judgments remain fixed while only the embedding function changes across runs. Such control is necessary if the benchmark is to support fit-for-purpose model selection rather than confound model comparison with changes in the evaluation dataset itself.

\subsection{Retrieval Evaluation Workflow}\label{retrieval-evaluation-workflow}

Once the vector collections are initialized, the pipeline executes the retrieval loop shown in Figure~\ref{fig:method_retrieval_workflow}. Each evaluation instance begins with a synthetic query drawn from the shared benchmark set. That query is submitted to a model-specific ChromaDB collection, where the embedding model under evaluation determines the vector representation used for search. The system then returns a ranked list of retrieved chunks under a fixed cutoff, ensuring that every model is tested at the same retrieval depth. The shared evaluation settings that constrain this loop are listed in Table~\ref{tbl:method_workflow_parameters}. \citep{ChromaDB_Docs}

The ranked results are subsequently aligned with the previously constructed qrels so that each query is interpreted against the same binary relevance resource, regardless of which embedding model produced the ranking. This ordering is methodologically important because corpus segmentation, query construction, and relevance judgments are all fixed before comparative retrieval begins. In combination with collection reinitialization, this design isolates representation quality from changes in benchmark artifacts or index state, allowing observed differences to be attributed more directly to the interaction between the candidate embedding model and the corpus.

The retrieval stage produces two classes of outputs. First, it emits evaluation-ready ranking artifacts that can be used in later scoring and comparative analysis. Second, it records timing traces associated with retrieval execution, thereby preserving operational evidence alongside effectiveness-oriented outputs. These timing by-products do not alter the retrieval protocol itself, but they allow the benchmark to support practical model selection under a single controlled workflow.

\subsection{Automated Reporting and Reproducibility}\label{automated-reporting-and-reproducibility}

The final stage transforms raw benchmark outputs into structured artifacts intended for manuscript analysis and engineering reuse. At the dataset level, the pipeline generates benchmark reports and accompanying visual summaries that document corpus characteristics, ranking artifacts, and timing traces. When multiple datasets are available, these dataset-level artifacts are consolidated into an aggregate report that supports cross-dataset inspection without altering the underlying per-dataset evidence. The method is designed for reproducibility at both the artifact and workflow levels. Intermediate benchmark resources are materialized as explicit corpus, query, and qrels artifacts; model evaluation is performed on isolated vector collections; and reporting outputs are stored as timestamped run products. The implementation of this pipeline is publicly available for inspection and reuse, which supports transparent reconstruction of the benchmarking workflow described in this manuscript. \citep{GitHub_RagRetrievalBench}
