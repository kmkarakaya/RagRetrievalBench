\section{Method}\label{method}

This study proposes a reusable, configuration-driven local benchmarking pipeline for selecting embedding models under corpus-specific RAG requirements. The central methodological premise is that a practitioner should not assume one embedding model will be suitable for every document collection under their control. Instead, each corpus is routed through the same staged workflow separately, producing its own chunked corpus, synthetic queries, relevance judgments, model-specific vector indexes, retrieval metrics, timing summaries, and a dataset-level report. Within a benchmark comparison, the selected candidate roster and protocol are held constant so that the corpus-specific reports remain comparable, but the primary model-selection artifact remains the report for the corpus being deployed. When heterogeneous corpus subsets are benchmarked separately, an aggregate report can provide secondary comparative context across topic- or language-specific partitions rather than a command to deploy one global model.

\subsection{Pipeline Overview}\label{pipeline-overview}

The pipeline operates at the dataset level and begins with explicit dataset routing, as illustrated in Figure~\ref{fig:method_pipeline_workflow}. Each corpus is processed, indexed, evaluated, and reported in isolation so that document inputs, chunked corpora, synthetic queries, qrels, vector collections, ranking artifacts, timing traces, and reports remain separated across datasets. This design reduces cross-dataset contamination and allows one practitioner to repeat the same methodological template for document collections that differ in language, domain, structure, or scale. After routing, the workflow advances through document ingestion, chunking, query generation, and relevance construction, thereby producing the benchmark artifacts required for comparative retrieval within that corpus.

Before a benchmark run, the practitioner selects the document collection and configures the candidate models and evaluation settings according to the intended comparison. Those choices define that experimental instantiation. Once the comparison begins, the selected values are held constant across candidate models and, when cross-corpus comparison is intended, across corpus runs. Thus, a \emph{fixed protocol} in this method denotes within-comparison experimental control rather than hard-coded pipeline parameters; a different configuration can be evaluated through a separate controlled run.

Once these corpus-level artifacts have been created, the pipeline branches into model-specific indexing and evaluation. Separate vector collections are built for each candidate embedding model, and each model from the shared roster is evaluated against the same frozen query and qrels resources for that corpus rather than against model-specific evaluation resources. Holding the selected configuration constant makes the resulting dataset-level reports comparable while preserving corpus-specific model selection as the primary objective. Retrieval evaluation is followed by an uncertainty stage that resamples the per-query metric values, so that each dataset report states not only how the candidates rank but which parts of that ranking the corpus actually resolves. The final stage consolidates the resulting outputs into dataset-level reports and, when multiple corpora are available, an optional aggregate comparison report. The sequence of stages and their intermediate products are summarized in Table~\ref{tbl:method_pipeline_stages} and illustrated conceptually in Figure~\ref{fig:method_pipeline_workflow}.

\subsection{Corpus Preparation}\label{corpus-preparation}

The first stage converts each local document collection into a benchmarkable text corpus. Source documents are ingested from the local corpus and parsed into textual segments; in the present experimental snapshot, these source documents are provided as PDF files. To preserve local context while keeping units manageable for downstream embedding models, the extracted text is segmented by recursive character-based chunking with controlled overlap between adjacent segments. This strategy reduces the probability that semantically dependent passages are split into entirely disconnected units, while still producing retrieval items that can be embedded and indexed efficiently. The fixed parameterization used in the experimental instantiation of this workflow is summarized in Section~\ref{shared-evaluation-setup}.

Dataset-level isolation is maintained during corpus preparation. Each dataset yields its own chunked corpus and retains its own storage path for downstream artifacts. As a result, the same pipeline can be reused across multiple corpora without mixing documents, collections, queries, qrels, indexes, evaluations, or reports between experiments.

\subsection{Synthetic Query and Relevance Construction}\label{synthetic-query-and-relevance-construction}

After corpus construction, the pipeline builds benchmark queries and relevance judgments through the sequence shown in Figure~\ref{fig:method_qrels_workflow}. The procedure assigns the language model two distinct roles that are kept terminologically separate throughout the paper: a \emph{query generator} that turns a seed passage into an information need, and a \emph{relevance judge} that labels candidate passages against that need. The two roles are separated deliberately because their validity concerns differ---query realism on one side, judgment reliability on the other---and should be examined independently.

For each dataset, construction proceeds in five steps:
\begin{enumerate}
\tightlist
\item \textbf{Seed sampling.} Sample seed chunks from the chunked corpus under a fixed random seed, one seed chunk per query and without replacement, so that each chunk seeds at most one query.
\item \textbf{Query generation.} For each seed chunk, prompt the query generator to produce one concise natural-language query in the same language as the seed. This anchors queries to the target corpus while avoiding the cost of manually authoring a query set for each new dataset.
\item \textbf{Pooled candidate retrieval.} For each query, form a candidate pool by taking the top-ranked chunks retrieved by \emph{every} evaluated embedding model and unioning them after deduplication. Pooling across all models, rather than trusting a single retriever, reduces the privilege given to any one evaluated model when constructing the candidate set. The pipeline builds a vector collection for each evaluated model to perform this retrieval; when collection reinitialization is enabled, these collections are rebuilt from scratch before the evaluation stage, so the indexes used for scoring are constructed independently of those used for pooling.
\item \textbf{Relevance judging.} Present each query--candidate pair to the relevance judge, which returns a binary label under a fixed instruction: a candidate is labeled relevant when it contains complete or partial information that helps answer the query, and non-relevant when it does not relate to the query.
\item \textbf{Qrels assembly.} Store the judgments as a qrels artifact that records \emph{both} positive and negative labels, so that non-relevant decisions remain auditable rather than discarded, and freeze the query set and qrels before any embedding model is scored so that every model is evaluated against the same relevance resource.
\end{enumerate}

By default, the seed chunk used to generate a query is not automatically assigned a positive relevance label. It is treated under the same retrieval-and-judging procedure as other chunks; consequently, a generated query may have no positive judgment if neither the seed nor another pooled candidate is judged relevant.

The concrete candidate-pool size and query count used in this paper are reported in Section~\ref{shared-evaluation-setup}, and the seed policy in Section~\ref{reproducibility-conditions}. Roster-wide pooling is a deliberate benchmark-design choice: as discussed in Section~\ref{related-work}, constructing qrels from a single retriever's candidate list can bias the evaluation toward that retriever. This pooling step bounds single-model bias within the evaluated roster, but it does not guarantee complete relevance coverage; relevant chunks outside the pooled candidate set can remain unjudged, a known limitation of pooled evaluation \citep{zobel1998reliable, buckley2004retrieval}. When the pool depth $p$ exceeds the scoring cutoff $k$, the judged pool is designed to cover each evaluated model's scored top-$k$ ranking; remaining pool incompleteness therefore chiefly concerns potentially relevant chunks that fall outside the union of the pooled top-$p$ rankings, rather than unjudged items within the rankings used for the reported top-$k$ metrics.

The workflow deliberately does not require a manually authored query set or human relevance labels as input. This reflects its intended use case: a practitioner begins with a local document collection for which a retrieval benchmark does not yet exist. Requiring a fully human-labeled benchmark before the pipeline can be used would make manual benchmark construction a prerequisite and substantially reduce the automation and scalability benefits that the workflow is intended to provide.

This design choice should not be interpreted as evidence that LLM-generated queries or judgments are equivalent to human labels. Query realism and judgment reliability remain separate validity questions, and human audit or judge calibration may be required when stronger assurance is needed.

The exact instructions used for query generation and relevance judgment in the reported snapshot, together with the corresponding model and decoding configuration, are included as versioned files in the public repository (\texttt{prompts/frozen\_snapshot/}, tag \texttt{frozen-snapshot-prompts}) \citep{GitHub_RagRetrievalBench}.

The query-generation and LLM-assisted relevance-construction stages build on the preliminary workflow in \citet{Karakaya_Conference_2025}, but they are used here inside a broader per-corpus selection pipeline with roster-wide pooling and dataset-level reporting.

\subsection{Embedding Index Construction}\label{embedding-index-construction}

The comparative evaluation stage uses a fixed set of sentence-transformer models spanning lightweight, higher-capacity, and multilingual alternatives within a single benchmarking design. Each model is assigned its own vector collection so that embedding generation, storage, and retrieval remain isolated across models. This separation is methodologically important because it prevents differences in shared or overwritten index state from confounding the comparison between embedding models. The exact benchmarked model roster is specified in the experimental setup \citep{SentenceTransformers_Pretrained}.

Model-specific collections are built from the same chunked corpus. This means that corpus content, query set, and relevance judgments remain fixed while only the embedding function changes across runs. Such control is necessary if the benchmark is to support fit-for-purpose model selection rather than confound model comparison with changes in the evaluation dataset itself.

\subsection{Retrieval Evaluation Workflow}\label{retrieval-evaluation-workflow}

Once the vector collections are initialized, the pipeline executes the retrieval loop shown in Figure~\ref{fig:method_retrieval_workflow}. Each evaluation instance begins with a synthetic query drawn from the shared benchmark set. That query is submitted to a model-specific ChromaDB collection \citep{ChromaDB_Docs}, where the embedding model under evaluation determines the vector representation used for search. The system then returns a ranked list of retrieved chunks under a fixed cutoff, ensuring that every model is tested at the same retrieval depth. The shared evaluation settings that constrain this loop are summarized in Section~\ref{shared-evaluation-setup}.

The ranked results are subsequently aligned with the previously constructed qrels so that each query is interpreted against the same binary relevance resource, regardless of which embedding model produced the ranking. This ordering is methodologically important because corpus segmentation, query construction, and relevance judgments are all fixed before comparative retrieval begins. In combination with collection reinitialization, this design isolates representation quality from changes in benchmark artifacts or index state, allowing observed differences to be attributed more directly to the interaction between the candidate embedding model and the corpus.

The retrieval stage produces two classes of outputs. First, it emits evaluation-ready ranking artifacts that are scored into retrieval metrics under the fixed cutoff; these per-query ranked lists are persisted for every model, which is what allows the uncertainty stage of Section~\ref{query-level-uncertainty} to resample the per-query metric values without repeating retrieval. Second, it records the implemented timing traces: combined corpus embedding and index-insertion timing for corpus construction, and combined query-embedding and vector-search latency for query execution. These timing by-products do not alter the retrieval protocol itself, but they allow the benchmark to preserve measured operational evidence alongside effectiveness-oriented outputs under a single controlled workflow.

\subsection{Query-Level Uncertainty Estimation}\label{query-level-uncertainty}

A ranking of point estimates does not by itself say whether a corpus is able to separate two candidate models, and a practitioner who acts on an unresolved difference may otherwise be given an overly confident impression of the ranking. The pipeline therefore treats uncertainty as an evaluation stage rather than as an optional post-hoc analysis. During retrieval evaluation, each model's per-query ranked list is persisted alongside the aggregate metrics, so the per-query metric values that the aggregate is built from remain available. This stage resamples those values and reports the result as part of the dataset-level artifact, which is the level at which the selection decision is made.

Two kinds of interval are produced, and they answer different questions. A \emph{marginal} interval describes how far a single model's score would move under resampling of the query set. Marginal intervals can overlap substantially because models evaluated on the same corpus are exposed to the same query-level difficulty variation. A \emph{paired} interval instead resamples the per-query differences between a model and the corpus's own leading candidate, which cancels the shared component. It therefore directly characterizes uncertainty in the query-level difference between the two candidates and is more informative for assessing whether an observed ranking gap is resolved by the available queries; overlap between two marginal intervals is consequently not evidence that two models perform alike. Both are reported so that the distinction remains visible to the reader rather than being resolved silently.

Resampling uses the percentile bootstrap with $B$ resamples at a configured coverage level, and the pipeline draws each (corpus, model, metric) cell from its own independently derived random stream. Queries are the resampling unit; for a paired comparison, the same resampled query indices are applied to both candidates and the bootstrap distribution is formed from their query-level metric differences. This makes the reported interval for a corpus independent of how many datasets were evaluated in the same invocation, of the order in which they were processed, and of which metrics were enabled: evaluating one corpus alone reproduces exactly the numbers obtained when evaluating all of them together. The alternative, a single stream consumed in traversal order, would make every reported interval depend on unrelated parts of the run and would not be reproducible from a partial re-execution.

The same estimator is applied at the aggregate level, with two properties that must be stated because they change interpretation. It is a pooled mean over all scored queries rather than the unweighted macro mean of the per-corpus means used elsewhere in the reports, so the two aggregate figures differ slightly. It is also unstratified: resampling draws uniformly from the concatenated per-query vector and does not preserve each corpus's share of the queries, so variation in corpus composition is folded into the aggregate interval widths. These intervals are descriptive and conditional on the snapshot; because queries are generated from corpus chunks, queries are nested within a small number of datasets, documents contribute related chunks, and relevance labels are model-assigned, they should not be read as population-level inference.

\subsection{Automated Reporting and Reproducibility}\label{automated-reporting-and-reproducibility}

The final stage transforms raw benchmark outputs into structured reporting artifacts intended for comparative analysis and engineering reuse. As illustrated in Figure~\ref{fig:method_reporting_workflow}, this workflow is organized in two reporting layers whose outputs are summarized in Table~\ref{tbl:method_reporting_outputs}, and both are generated from stored artifacts rather than from transient run state. At the end of retrieval evaluation the pipeline first materializes the complete evaluation record as a machine-readable results file: the applied configuration, corpus and query statistics, qrels composition, per-model retrieval metrics, per-query rankings, timing measurements, and an environment snapshot. Every subsequent reporting product is derived from that file, which is why a report can be regenerated, or a reporting option changed, without repeating retrieval.

The first layer operates separately for each dataset or dataset subset. When the objective is to select a suitable embedding model for one available corpus, or for a representative sample drawn from that corpus, the pipeline can terminate at this stage. The generated dataset report is a self-contained document: it restates the configuration and model roster under which the corpus was evaluated, describes the corpus, query set, and relevance-judgment composition, presents the per-model retrieval metrics together with the marginal and paired query-level intervals of Section~\ref{query-level-uncertainty} and a pairwise difference summary, reports embedding throughput and query latency, and closes with the corpus-specific reading and its limitations. Metric-profile and timing charts are emitted alongside it. These per-dataset artifacts preserve the full evaluation trace for one corpus under the shared model roster and provide the self-contained basis for a corpus-specific shortlist within that local context.

The second layer begins only after one or more dataset-level reports have been completed. This aggregation stage is optional secondary context for settings in which the available collection is heterogeneous, for example when documents belong to different topic classes such as finance, law, or administration, or when the corpus spans multiple languages such as English, Turkish, or French. In such cases, a practitioner may evaluate heterogeneous language or domain subsets separately, generate a dataset report for each subset, and then combine the completed reports into an aggregate comparison package, as shown in Figure~\ref{fig:method_reporting_workflow}. The aggregate report is therefore derived from completed benchmark products rather than from raw retrieval outputs: it loads the stored per-dataset result files and reports cross-dataset rankings by average rank, per-dataset model performance, embedding-speed and latency comparisons, pooled query-level intervals, and a per-dataset recapitulation, so that cross-corpus behavior can be inspected without overriding the corpus-specific shortlist produced by each dataset-level report. The concrete experimental configuration and the resulting comparative evidence are presented in Sections~\ref{experiments} and~\ref{results}, respectively.

The method is designed for reproducibility at both the artifact and workflow levels. Intermediate benchmark resources are materialized as explicit corpus, query, qrels, ranking, timing, and report artifacts; model evaluation is performed on isolated vector collections; and reporting outputs are stored as timestamped run products at both dataset and aggregate levels. The implementation of this pipeline is publicly available for inspection and reuse, which supports transparent reconstruction of the workflow described in this paper. This availability does not, however, guarantee that external services and model aliases used by the pipeline will remain unchanged.

\subsection{Applying the Pipeline to a New Corpus}\label{applying-the-pipeline}

The workflow is distributed as a command-line tool, and the stages of Table~\ref{tbl:method_pipeline_stages} map onto its invocations. A practitioner supplies a directory of source documents for the new corpus and sets, in one configuration file, the candidate model roster, chunking parameters, query count, candidate-pool depth, retrieval cutoff, and judge settings. A new corpus can be registered through its input directory and configuration without modifying the pipeline code; dataset routing derives the corresponding working paths automatically.

Table~\ref{tbl:method_invocations} lists the invocations. The two language-model stages---query generation and relevance judging---may be run synchronously for small corpora or submitted as batch jobs for larger ones; this is the only point at which the execution mode varies. The batch-mode end-to-end invocation reuses an existing corpus, query set, or qrels artifact rather than regenerating it, so an interrupted run is resumed by repeating the same command. This reuse is based on the artifact's presence, not on a check against the current configuration; after a configuration change, the affected artifacts and their downstream products must therefore be regenerated. Because each stage writes its artifact to disk before the next begins, a practitioner can stop after relevance construction to inspect the generated queries and judgments before committing to the evaluation stages, or re-run only the uncertainty and reporting stages after changing a reporting option---neither re-embeds the corpus nor issues further language-model calls.
